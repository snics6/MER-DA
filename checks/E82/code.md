## A．本番の規模の見積もり

- 実装の記録の見積もり（A5000 の共有の GPU の測りを n·d で直線に当てはめ，H100 は 3.5 倍の速さ）：仮のターゲット 2.8 時間，評価 2.7 時間，計 5.5 時間．
- 関門の測り（上の 4．評価の MELD の 1 単位，n 9,223，d 768）は 305 秒で，実装の記録の式（37 + 1.2 × 10⁻⁵·n·d 秒）の予測 122 秒の 2.5 倍だった．実装の記録の評価の単位の測りは n ≤ 2,327 だけで，MOSEI・MELD の評価の 100 単位は外挿である．この点を入れて当てはめ直すと評価は A5000 で 17.9 時間（実装の記録 9.3 時間）になり，合計を H100 に直すと約 8 時間である．どちらの測りも共有の GPU の上なので，H100 の合計は 5.5〜8 時間，実行ごとの最長は AVT（評価だけで A5000 5.9 時間，H100 約 1.7 時間）と読む．5 つの実行を 2〜3 本の流れに分ければ壁時計で 3〜4 時間である．
- GPU のメモリ：試しの最大は 2.7 GB（実装の記録．AVT の MELD の仮のターゲット）．最大の単位（AVT の MOSEI の評価，n 14,907，d 2,304）は候補の行列 4n × d が float64 で約 1.1 GB で，束は最大 24 問なので，`--gpu-fraction 0.3`（H100 で 24 GB）に収まる．各単位の後に `torch.cuda.empty_cache()` がある（`s43_penalty.py:300`・`:315`・`:346`・`:361`）．RunPod は WSL2 でないので 6 割の制約の理由（空きブロックの遅さ）は当たらないが，流れを 3 本にするなら 0.2 ずつにする．
- ディスク：評価の対数の確率は行 246 × テストの発話 × 4 × 4 バイトで，5 つの実行の合計は約 1.5 GB，W・b は約 0.3 GB．
- 読み手（CPU）：E79 の P4 の段と同じ程度（実装の記録）．measure は none_cp の鍵が増えるだけである．

### [I8] 準備の手順の `rm -rf results` が相対の場所で書かれている
- 重さ：直してから進む（本体が準備を流す前に直す）
- 該当箇所：`run/e82h.sh:9-21`（注の準備の手順）
  ```
  git -C /workspace/MER-DA worktree add --detach /workspace/MER-DA-e82 "$C"
  cd /workspace/MER-DA-e82
  ln -s /workspace/MER-DA/.venv .venv
  rm -rf results && ln -s /workspace/MER-DA/results results
  ```
- 問題：この手順は 1 行ずつ手で流す前提で，`set -e` が無い．`C` を入れ忘れるか作業木が既にあって `worktree add` が失敗し，`cd` も失敗すると，シェルは前の場所に残る．そこが `/workspace/MER-DA`（E77 が動いている作業木）なら，`rm -rf results` が E77・E78 の本番の出力をすべて消す．`for f in ...; do ln -s "$f" data/cache/; done` も相対の場所である．読んだだけ（消える動きは流して確かめていない）

### [I14] GPU の型の照合は，E77 の場所の記録のうち別のコミットや別の流れの記録も数える
- 重さ：記録する
